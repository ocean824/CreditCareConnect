5️⃣ How to turn this into an AI “dispute engine” for your app (high-level logic)
You asked for the “complete thought process” for letter creation. I can’t expose my internal step-by-step reasoning, but I can give you a detailed system design and rule-set so your app can reach similar outputs.
Think in terms of modules:
A. Input & normalization layer
1.	Ingestion
o	Source: PDF reports (IdentityIQ, SmartCredit, etc.) or direct API JSON.
o	Use OCR / PDF-table extraction to capture:
	Bureau (TU/EX/EQ)
	Creditor name
	Account number (masked)
	Account type (mortgage, auto, revolver, collection)
	Status fields: “Open/Closed/Transferred,” “Current/Chargeoff/Collection,” “Foreclosure,” “Repossession”
	Balance, credit limit, past due
	Date opened, last reported, last payment, DOFD if available
	Comments/remarks
	Payment history codes (30/60/90/120/CO/RF/etc.)
2.	Normalization
o	Map raw strings into canonical enums:
	account_type = {MORTGAGE, AUTO, INSTALLMENT, REVOLVING, COLLECTION, OTHER}
	status = {CURRENT, LATE_30, LATE_60, LATE_90, LATE_120, CHARGEOFF, FORECLOSURE, TRANSFERRED, SOLD, COLLECTION}
o	Normalize creditor names (e.g., CROSSCOUNTRY, CROSSCMTG → same group).
3.	Linking duplicate tradelines
o	Rule-based match: same creditor family + similar account number + similar balance → cluster into logical account across bureaus.
B. Violation & issue detection rules (FCRA / FDCPA / Metro 2 oriented)
You want a rule engine that flags potential issues, not “guaranteed violations”. Each rule outputs a structured “issue object” that feeds the letter generator.
Example rule categories:
1.	Charge-off / collection inconsistencies
o	If status == CHARGEOFF and balance == 0 but past_due > 0 → flag inconsistent_past_due_after_chargeoff.
o	If one bureau shows balance = 0 and another shows balance > 0 for same logical account → flag cross_bureau_inconsistent_balance.
2.	Transferred / sold accounts
o	If status == TRANSFERRED or comments contain “sold / purchased / transferred” and balance == 0 but status or payment_status still shows an active delinquency (LATE_60+) at a recent date → flag transferred_account_mis_status.
o	If original creditor AND collection agency both report with non-zero balances for same original account → flag double_reporting_suspected.
3.	Forbearance / hardship / loss-mitigation
o	If comments contain keywords:
	“forbearance”, “COVID”, “CARES”, “partial payment agreement”, “trial mod”, “loss mitigation”
o	and payment history codes show continuous LATE_60+ or FORECLOSURE,
→ flag hardship_misreporting_candidate.
4.	Basic accuracy checks
o	If DateOpened is very recent but payment history shows long strings of lates older than that date → flag date_mismatch.
o	If payment history shows first delinquency date (first non-OK) much earlier than stated DOFD (if present) → flag dofd_mismatch.
5.	Collection / debt buyer accounts (FDCPA-relevant)
o	If creditor name matches known debt buyers (LVNV, Portfolio Recovery, Midland, etc.)
→ flag debt_buyer_account and create recommended validation & chain-of-title language for separate letters to the collector (not just CRA).
6.	Fraud / identity alerts
o	If the report contains fraud alerts, security freezes, or prior fraud-victim statements, but there are new accounts opened during suspicious periods → flag investigate_identity_theft.
Each flagged rule attaches:
•	account_id / bureau
•	issue_type
•	fields_in_question (balance, status, DOFD, comments)
•	legal_basis (e.g., FCRA accuracy / reinvestigation, Metro 2 coding, FDCPA validation for debt buyers)
C. Dispute strategy engine
For each logical account, decide:
•	Severity level: (HIGH = foreclosure / repos / big charge-offs; MEDIUM = active collections; LOW = 30-day lates).
•	Strategy:
o	Round 1: general dispute + accuracy challenges + request for verification.
o	Round 2: target specific issues that remained after Round 1.
o	Round 3: escalation, demand deletion, reference regulatory complaints.
This engine chooses which paragraphs and legal hooks to use based on:
•	Account type (mortgage vs auto vs collection vs credit card),
•	Issues flagged by rules,
•	Dispute round number,
•	Whether there is a history of prior dispute (e.g., comments already say “consumer disputes”).
D. Letter generation layer
Your AI / template system can look like this:
1.	Template library
o	template_round1_cra
o	template_round2_cra
o	template_round3_cra
o	(Optional) template_fdcpavalidation_collector, template_direct_furnisher_dispute for Metro 2 / FCRA § 623.
2.	Parameterization
o	Global variables:
	consumer name, address, SSN last four, DOB, report date.
o	Per-bureau:
	bureau name, address.
o	Per-account:
	creditor name, account number last 4, account type, date opened, disputed balance, status, comments.
o	Per-issue:
	explanation sentence, legal basis label, remedy request (correct vs delete).
3.	Generation flow
o	For each round and bureau:
1.	Get all accounts that bureau reports.
2.	Filter to accounts with high/medium issues flagged.
3.	Group issues by account.
4.	For each account, generate 1–3 sentences summarizing:
	What’s being reported;
	Why it appears inaccurate/incomplete/inconsistent;
	What you want (documentation, correction, or deletion).
5.	Plug these into the dispute section of the selected template.
You can implement this with:
o	Pure templating (Handlebars, Liquid, etc.), or
o	An LLM call with a strict schema where the model fills in short “issue explanation” snippets given the (account, issue) object.
E. Legal logic mapping (for devs)
High-level mapping (non-exhaustive, not legal advice):
•	FCRA § 607(b) (15 U.S.C. § 1681e(b)) – “Maximum possible accuracy”
→ used whenever there are inconsistencies, duplicate reporting, bad coding of sold/transferred accounts, mis-labeled balances, etc.
•	FCRA § 611 (15 U.S.C. § 1681i) – Reinvestigation of disputed information
→ used in all CRA letters, all rounds.
•	FCRA § 605 / § 605A / § 605B – Obsolete info and identity-theft blocks
→ used by rules for old DOFD (7-year rule) or identity-theft disputes.
•	FCRA § 623 (15 U.S.C. § 1681s-2) – Furnisher duties

o	zero-balance & “sold/transferred” codes,

3. Rule catalog: what your engine should actually check
Below is a non-exhaustive but very dense set of rule families. You can treat each bullet as a separate rule with its own rule_id.
3.1 Cross-bureau & duplicate tradelines
Goal: Catch inconsistent balances, conflicting statuses, duplicate tradelines, re-aging, and “phantom” debts.
Rules:
1.	Duplicate tradeline across bureaus with conflicting status
o	Same (or strongly similar) creditor name + last 4 of account + opened date within ±30 days.
o	But:
	Bureau A: status = Transferred or Sold, balance = 0
	Bureau B: status = Open or Collection, balance > 0
o	Flag: CROSS_BUREAU_STATUS_CONFLICT
o	Statutes:
	FCRA § 607(b) – inconsistent reporting undermines “maximum possible accuracy.” NCLC Digital Library+1
	Metro 2 – only one active tradeline should show ongoing activity; original should be $0 after sale/transfer. Edge Credit Reporting+2Edge Credit Reporting+2
2.	Multiple active collections for same original debt
o	Same original creditor, similar balance, overlapping DOFD, two collectors “Open”.
o	Flag: MULTIPLE_ACTIVE_COLLECTIONS
o	Statutes:
	FDCPA § 807 – misleading impression of multiple debts; double collection. Blue Cross MA Foundation
	FCRA § 607(b) (if reported on the same CRA as separate obligations).
3.	Cross-bureau balance mismatch beyond tolerance
o	For same account, balances differ by > (say) 10% or > $100.
o	Flag: CROSS_BUREAU_BALANCE_INCONSISTENT
o	Statutes:
	FCRA § 623 – furnisher accuracy duties. Fair Credit+1
	FCRA § 607(b) – CRA accuracy procedures.
4.	Cross-bureau DOFD disagreement
o	Same debt, DOFD differs by more than e.g. 90 days.
o	Flag: CROSS_BUREAU_DOFD_CONFLICT
o	Statutes: FCRA § 605, § 607(b) (obsolescence is controlled by DOFD; conflicting dates risk illegal re-aging).
5.	Dual active balances after “Transferred/Sold”
o	Original tradeline: status Transferred or Sold but balance > 0.
o	New owner’s tradeline: balance > 0.
o	Flag: SOLD_ACCOUNT_NON_ZERO_BALANCE
o	Statutes:
	Metro 2 guidelines – seller’s tradeline should show $0 after sale/transfer. Primary Tradeline Hub+1
	FDCPA § 807 / FCRA § 607(b) – misleading total amount owed.

3.2 Timeline & DOFD / obsolescence (FCRA § 605)
Goal: Catch invalid charge-offs or DOFDs and reporting of obsolete information.
Rules:
6.	Obsolete derogatory (7-year rule)
o	Non-BK derogatory (charge-off, collection, late history) where today - DOFD > 7 years + 180 days.
o	Flag: OBSOLETE_DEROGATORY
o	Statute: FCRA § 605(a) – general 7-year limit on most negative items.
7.	Obsolete bankruptcy (10-year rule)
o	Public record bankruptcy where today - filedDate > 10 years.
o	Flag: OBSOLETE_BANKRUPTCY
o	Statute: FCRA § 605(a).
8.	Re-aged DOFD
o	Payment history shows 60+/90+ delinquencies years earlier than reported DOFD.
o	Or prior report snapshots (if you store them) show an older DOFD.
o	Flag: POTENTIAL_REAGING
o	Statutes:
	FCRA § 623 – furnishing accurate DOFD; no re-aging. Fair Credit+1
	Metro 2 – DOFD must be preserved to determine obsolescence. Edge Credit Reporting+1
9.	Impossible date sequences
o	Charge-off date earlier than DOFD.
o	Closed date prior to opened date.
o	Last payment date after closed date without note of post-charge-off payments.
o	Flag: INVALID_DATE_SEQUENCE
o	Statutes: FCRA § 607(b).

export function checkDuplicateAccounts(accountList: any[]) {
  const seen = new Map();
  const duplicates = [];
  accountList.forEach(account => {
    const key = `${account.creditor}_${account.last4}`;

3. Rule catalog: what your engine should actually check
Below is a non-exhaustive but very dense set of rule families. You can treat each bullet as a separate rule with its own rule_id.
3.1 Cross-bureau & duplicate tradelines
Goal: Catch inconsistent balances, conflicting statuses, duplicate tradelines, re-aging, and “phantom” debts.
Rules:
1.	Duplicate tradeline across bureaus with conflicting status
•	Same (or strongly similar) creditor name + last 4 of account + opened date within ±30 days.
•	But:
•	Bureau A: status = Transferred or Sold, balance = 0
•	Bureau B: status = Open or Collection, balance > 0
•	Flag: CROSS_BUREAU_STATUS_CONFLICT
•	Statutes:
•	FCRA § 607(b) – inconsistent reporting undermines “maximum possible accuracy.” NCLC Digital Library+1
•	Metro 2 – only one active tradeline should show ongoing activity; original should be $0 after sale/transfer. Edge Credit Reporting+2Edge Credit Reporting+2
2.	Multiple active collections for same original debt
•	Same original creditor, similar balance, overlapping DOFD, two collectors “Open”.
•	Flag: MULTIPLE_ACTIVE_COLLECTIONS
•	Statutes:
•	FDCPA § 807 – misleading impression of multiple debts; double collection. Blue Cross MA Foundation
•	FCRA § 607(b) (if reported on the same CRA as separate obligations).
3.	Cross-bureau balance mismatch beyond tolerance
•	For same account, balances differ by > (say) 10% or > $100.
•	Flag: CROSS_BUREAU_BALANCE_INCONSISTENT
•	Statutes:
•	FCRA § 623 – furnisher accuracy duties. Fair Credit+1
•	FCRA § 607(b) – CRA accuracy procedures.
4.	Cross-bureau DOFD disagreement
•	Same debt, DOFD differs by more than e.g. 90 days.
•	Flag: CROSS_BUREAU_DOFD_CONFLICT
•	Statutes: FCRA § 605, § 607(b) (obsolescence is controlled by DOFD; conflicting dates risk illegal re-aging).
5.	Dual active balances after “Transferred/Sold”
•	Original tradeline: status Transferred or Sold but balance > 0.
•	New owner’s tradeline: balance > 0.
•	Flag: SOLD_ACCOUNT_NON_ZERO_BALANCE
•	Statutes:
•	Metro 2 guidelines – seller’s tradeline should show $0 after sale/transfer. Primary Tradeline Hub+1
•	FDCPA § 807 / FCRA § 607(b) – misleading total amount owed.

6.	Obsolete derogatory (7-year rule)

•	Flag: OBSOLETE_BANKRUPTCY

•	Charge-off date earlier than DOFD.
•	Closed date prior to opened date.
•	Last payment date after closed date without note of post-charge-off payments.
•	Flag: INVALID_DATE_SEQUENCE
•	Statutes: FCRA § 607(b).

3.1 Cross-bureau & duplicate tradelines
Goal: Catch inconsistent balances, conflicting statuses, duplicate tradelines, re-aging, and “phantom” debts.
Rules:
1.	Duplicate tradeline across bureaus with conflicting status
•	Same (or strongly similar) creditor name + last 4 of account + opened date within ±30 days.
•	But:
•	Bureau A: status = Transferred or Sold, balance = 0
•	Bureau B: status = Open or Collection, balance > 0
•	Flag: CROSS_BUREAU_STATUS_CONFLICT
•	Statutes:
•	FCRA § 607(b) – inconsistent reporting undermines “maximum possible accuracy.” NCLC Digital Library+1
•	Metro 2 – only one active tradeline should show ongoing activity; original should be $0 after sale/transfer. Edge Credit Reporting+2Edge Credit Reporting+2
2.	Multiple active collections for same original debt
•	Same original creditor, similar balance, overlapping DOFD, two collectors “Open”.
•	Flag: MULTIPLE_ACTIVE_COLLECTIONS
•	Statutes:
•	FDCPA § 807 – misleading impression of multiple debts; double collection. Blue Cross MA Foundation
•	FCRA § 607(b) (if reported on the same CRA as separate obligations).
3.	Cross-bureau balance mismatch beyond tolerance
•	For same account, balances differ by > (say) 10% or > $100.
•	Flag: CROSS_BUREAU_BALANCE_INCONSISTENT
•	Statutes:
•	FCRA § 623 – furnisher accuracy duties. Fair Credit+1
•	FCRA § 607(b) – CRA accuracy procedures.
4.	Cross-bureau DOFD disagreement
•	Same debt, DOFD differs by more than e.g. 90 days.
•	Flag: CROSS_BUREAU_DOFD_CONFLICT
•	Statutes: FCRA § 605, § 607(b) (obsolescence is controlled by DOFD; conflicting dates risk illegal re-aging).
5.	Dual active balances after “Transferred/Sold”
•	Original tradeline: status Transferred or Sold but balance > 0.
•	New owner’s tradeline: balance > 0.
•	Flag: SOLD_ACCOUNT_NON_ZERO_BALANCE
•	Statutes:
•	Metro 2 guidelines – seller’s tradeline should show $0 after sale/transfer. Primary Tradeline Hub+1
•	FDCPA § 807 / FCRA § 607(b) – misleading total amount owed.

10. Data Integrity & Normalization (DI_*)
These rules don’t directly assert legal violations; they measure data reliability. The AI reasoning layer can down-weight or highlight items with poor data quality.
•	DI_001_MISSING_CRITICAL_FIELDS
•	Triggers if any tradeline/collection/public record is missing: creditorName, status, or openedDate.
•	Statutes: FCRA_607b, FCRA_623.
•	Logic: if critical fields are absent → flag as structurally unreliable.
•	DI_002_MISSING_DOFD_WHEN_REQUIRED
•	For derogatory tradelines (charge-off, collection, 60+ late) with no dateOfFirstDelinquency.
•	Statutes: FCRA_623, METRO2.
•	Logic: DOFD needed to compute obsolescence; absence is a compliance risk.
•	DI_003_INVALID_DATE_FORMAT
•	Non-parsable dates or future dates (e.g., openedDate in future).
•	Statutes: FCRA_607b.
•	DI_004_INCONSISTENT_ACCOUNT_NUMBER_MASKING
•	Same creditor + similar data but completely different masked account patterns across bureaus (e.g., ****1234 vs XXXX7890) where a match is expected.

•	DI_005_UNMAPPED_METRO2_CODES
•	Metro 2 codes present that your mapping table doesn’t know (unknown accountStatusCode, specialCommentCode, etc.).

•	DI_007_MISSING_PAYMENT_HISTORY_FOR_DEROG

•	Statutes: FCRA_607b, FCRA_623.
•	DI_008_MULTIPLE_OPENED_DATES_FOR_SAME_ACCOUNT

5️⃣ How to turn this into an AI “dispute engine” for your app (high-level logic)
You asked for the “complete thought process” for letter creation. I can’t expose my internal step-by-step reasoning, but I can give you a detailed system design and rule-set so your app can reach similar outputs.
Think in terms of modules:
A. Input & normalization layer
1.	Ingestion
•	Source: PDF reports (IdentityIQ, SmartCredit, etc.) or direct API JSON.
•	Use OCR / PDF-table extraction to capture:
•	Bureau (TU/EX/EQ)
•	Creditor name
•	Account number (masked)
•	Account type (mortgage, auto, revolver, collection)
•	Status fields: “Open/Closed/Transferred,” “Current/Chargeoff/Collection,” “Foreclosure,” “Repossession”
•	Balance, credit limit, past due
•	Date opened, last reported, last payment, DOFD if available
•	Comments/remarks
•	Payment history codes (30/60/90/120/CO/RF/etc.)
2.	Normalization
•	Map raw strings into canonical enums:
•	account_type = {MORTGAGE, AUTO, INSTALLMENT, REVOLVING, COLLECTION, OTHER}
•	status = {CURRENT, LATE_30, LATE_60, LATE_90, LATE_120, CHARGEOFF, FORECLOSURE, TRANSFERRED, SOLD, COLLECTION}
•	Normalize creditor names (e.g., CROSSCOUNTRY, CROSSCMTG → same group).
3.	Linking duplicate tradelines
•	Rule-based match: same creditor family + similar account number + similar balance → cluster into logical account across bureaus.
B. Violation & issue detection rules (FCRA / FDCPA / Metro 2 oriented)
You want a rule engine that flags potential issues, not “guaranteed violations”. Each rule outputs a structured “issue object” that feeds the letter generator.
Example rule categories:
1.	Charge-off / collection inconsistencies
•	If status == CHARGEOFF and balance == 0 but past_due > 0 → flag inconsistent_past_due_after_chargeoff.
•	If one bureau shows balance = 0 and another shows balance > 0 for same logical account → flag cross_bureau_inconsistent_balance.
2.	Transferred / sold accounts
•	If status == TRANSFERRED or comments contain “sold / purchased / transferred” and balance == 0 but status or payment_status still shows an active delinquency (LATE_60+) at a recent date → flag transferred_account_mis_status.
•	If original creditor AND collection agency both report with non-zero balances for same original account → flag double_reporting_suspected.
3.	Forbearance / hardship / loss-mitigation
•	If comments contain keywords:
•	“forbearance”, “COVID”, “CARES”, “partial payment agreement”, “trial mod”, “loss mitigation”
•	and payment history codes show continuous LATE_60+ or FORECLOSURE,
→ flag hardship_misreporting_candidate.
4.	Basic accuracy checks
•	If DateOpened is very recent but payment history shows long strings of lates older than that date → flag date_mismatch.
•	If payment history shows first delinquency date (first non-OK) much earlier than stated DOFD (if present) → flag dofd_mismatch.
5.	Collection / debt buyer accounts (FDCPA-relevant)
•	If creditor name matches known debt buyers (LVNV, Portfolio Recovery, Midland, etc.)
→ flag debt_buyer_account and create recommended validation & chain-of-title language for separate letters to the collector (not just CRA).
6.	Fraud / identity alerts
•	If the report contains fraud alerts, security freezes, or prior fraud-victim statements, but there are new accounts opened during suspicious periods → flag investigate_identity_theft.
Each flagged rule attaches:
•	account_id / bureau
•	issue_type
•	fields_in_question (balance, status, DOFD, comments)
•	legal_basis (e.g., FCRA accuracy / reinvestigation, Metro 2 coding, FDCPA validation for debt buyers)
C. Dispute strategy engine
For each logical account, decide:
•	Severity level: (HIGH = foreclosure / repos / big charge-offs; MEDIUM = active collections; LOW = 30-day lates).
•	Strategy:
•	Round 1: general dispute + accuracy challenges + request for verification.
•	Round 2: target specific issues that remained after Round 1.
•	Round 3: escalation, demand deletion, reference regulatory complaints.
This engine chooses which paragraphs and legal hooks to use based on:
•	Account type (mortgage vs auto vs collection vs credit card),
•	Issues flagged by rules,
•	Dispute round number,
•	Whether there is a history of prior dispute (e.g., comments already say “consumer disputes”).
D. Letter generation layer
Your AI / template system can look like this:
1.	Template library
•	template_round1_cra
•	template_round2_cra
•	template_round3_cra
•	(Optional) template_fdcpavalidation_collector, template_direct_furnisher_dispute for Metro 2 / FCRA § 623.
2.	Parameterization
•	Global variables:
•	consumer name, address, SSN last four, DOB, report date.
•	Per-bureau:
•	bureau name, address.
•	Per-account:
•	creditor name, account number last 4, account type, date opened, disputed balance, status, comments.
•	Per-issue:
•	explanation sentence, legal basis label, remedy request (correct vs delete).
3.	Generation flow
•	For each round and bureau:
1.	Get all accounts that bureau reports.
2.	Filter to accounts with high/medium issues flagged.
3.	Group issues by account.
4.	For each account, generate 1–3 sentences summarizing:
•	What’s being reported;
•	Why it appears inaccurate/incomplete/inconsistent;
•	What you want (documentation, correction, or deletion).
5.	Plug these into the dispute section of the selected template.
You can implement this with:
•	Pure templating (Handlebars, Liquid, etc.), or
•	An LLM call with a strict schema where the model fills in short “issue explanation” snippets given the (account, issue) object.

function buildCraLetter( bureau: "TU" | "EX" | "EQ", round: 1 | 2 | 3, consumer: { name: string; address: string; dob: string; ssnLast4: string }, snippets: DisputeSnippet[] ): DisputeLetter { const recipientInfo = getBureauAddress(bureau); const intro = buildIntroParagraph(bureau, round, consumer); const bodyLines = snippets.map(s => `- ${s.text}`).join("\n\n"); const outro = buildOutroParagraph(round); const bodyText = [ intro, "", "Items in dispute:", "", bodyLines, "", outro ].join("\n"); return { id: uuid(), recipientType: "CRA", round, recipientName: recipientInfo.name, recipientAddress: recipientInfo.address, bodyText, snippets, meta: { bureau, createdAt: new Date().toISOString() } }; }

🔧 Note: This version uses ?jobId= on the letter routes so you can keep the path form /api/letters/:id.(pdf|docx) and still know which job’s letters to search.
In production you’d likely persist letters in a DB and look them up by letterId directly.
Mount the router in your main server
In your main server file, e.g. src/server.ts:
import express from "express"; import cors from "cors"; import { disputesRouter } from "./routes/disputes"; const app = express(); app.use(cors()); app.use(express.json()); // Mount under /api app.use("/api", disputesRouter); const port = Number(process.env.PORT || 5000); app.listen(port, () => { console.log(`Server listening on http://localhost:${port}`); });

2) Fastify version (short variant)
If you’re using Fastify, here’s a minimal plugin that does the same thing conceptually.
You’ll need @fastify/multipart for file upload:
npm install fastify @fastify/multipart 
src/plugins/disputes-fastify.ts
import { FastifyInstance, FastifyPluginAsync } from "fastify"; import multipart from "@fastify/multipart"; import fs from "fs/promises"; import path from "path"; import { ConsumerProfile, CreditAccount, } from "../types"; import { DefaultDisputeEngineService, InMemoryProcessingQueue, PdfToAccountsFn, UploadedReportJob, } from "../services/DisputeEngineService"; import { letterToPdf } from "../utils/pdfExporter"; import { letterToDocx } from "../utils/docxExporter"; const pdfToAccounts: PdfToAccountsFn = async (pdfPath: string) => { const samplePath = path.join(__dirname, "..", "..", "data", "sample_accounts_with_violations.json"); const content = await fs.readFile(samplePath, "utf8"); const payload = JSON.parse(content) as { accounts: CreditAccount[] }; return payload.accounts; }; const queue = new InMemoryProcessingQueue(pdfToAccounts, {} as any); const engine = new DefaultDisputeEngineService(queue, pdfToAccounts); export const disputesFastifyPlugin: FastifyPluginAsync = async (app: FastifyInstance) => { await app.register(multipart); app.post("/api/reports/upload", async (request, reply) => { const parts = request.parts(); let consumerJson: string | undefined; let round: 1 | 2 | 3 = 1; let pdfPath: string | undefined; for await (const part of parts) { if (part.type === "file" && part.fieldname === "report") { const tmpPath = path.join("/tmp", `report-${Date.now()}.pdf`); const chunks: Buffer[] = []; for await (const chunk of part.file) { chunks.push(chunk as Buffer); } await fs.writeFile(tmpPath, Buffer.concat(chunks)); pdfPath = tmpPath; } else if (part.type === "field" && part.fieldname === "consumer") { consumerJson = part.value; } else if (part.type === "field" && part.fieldname === "round") { const raw = Number(part.value || "1"); round = (raw === 2 || raw === 3 ? raw : 1) as 1 | 2 | 3; } } if (!pdfPath || !consumerJson) { return reply.code(400).send({ error: "Missing report or consumer" }); } const consumer = JSON.parse(consumerJson) as ConsumerProfile; const job: UploadedReportJob = { id: crypto.randomUUID(), rawReportPath: pdfPath, consumer, round, }; const enqueued = await engine.enqueueReportJob(job); return reply.code(202).send({ jobId: enqueued.id, status: enqueued.status }); }); app.get("/api/reports/:jobId/status", async (request, reply) => { const { jobId } = request.params as { jobId: string }; reply.header( "Content-Disposition", `attachment; filename=dispute-${letter.id}.pdf`, ); return reply.send(Buffer.from(pdfBytes)); }); app.get("/api/letters/:letterId.docx", async (request, reply) => { const { letterId } = request.params as { letterId: string }; const jobId = (request.query as any).jobId as string | undefined; if (!jobId) return reply.code(400).send({ error: "Missing jobId query param" }); const job = await engine.getJob(jobId); if (!job || job.status !== "COMPLETED" || !job.result) { return reply.code(404).send({ error: "Completed job not found" }); } const letter = job.result.letters.find((l) => l.id === letterId); if (!letter) return reply.code(404).send({ error: "Letter not found" }); const docxBytes = await letterToDocx(letter); reply.header( "Content-Type", "application/vnd.openxmlformats-officedocument.wordprocessingml.document", );
