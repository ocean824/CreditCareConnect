2. How the production pipeline now works (end-to-end)

Upload credit report → Advanced AI analysis → Violations → Letters

Upload & Parse

Endpoint: POST /api/credit-reports/upload (in server/routes.ts)

Flow:

Saves the raw report file + text.

Calls parseCreditReportText(...) in server/services/creditReportParser.ts.

Uses GPT-5.1 Chat to convert raw report text → normalized JSON:

bureaus[]

tradelines[]

collections[]

publicRecords[]

inquiries[]

Rules Engine + AI Legal Layer

After parsing, the app triggers the advanced analysis:

runAllRules(...) from server/rules/engine.ts

Uses FCRA/FDCPA/Metro 2–aware rules defined in:

server/rules/*.ts (e.g. rules_status.ts, rules_balances.ts)

Catalog in server/config/rules_catalog.json (contains FCRA, Metro2, FDCPA statute codes).

generateAiExplanations(...) from server/services/advancedCreditAnalysis.ts

Uses GPT-5.1 Chat with a structured prompt to:

Explain each rule hit

Attach human-readable explanations

Attach relevant statute citations (FCRA, Metro 2, FDCPA, etc.)

Recommend dispute angle & priority

Results are stored via DatabaseStorage (server/storage.ts) into:

analysisRuns

issues

aiIssueExplanations

Legacy violations table for the letters UI

Violations surfaced to frontend

Endpoint: GET /api/violations

Implementation: storage.getViolationsByUserId(userId):

Joins violations → creditReports by user

Returns per-bureau violations with:

accountName

accountNumber

bureau

violationType

description

statute (FCRA / FDCPA / Metro2 id)

severity, status

Frontend: client/src/pages/letters.tsx

Uses React Query: useQuery<Violation[]>({ queryKey: ["/api/violations"], ... })

Feeds the Create / Generate Letter UI.

Create & populate letters ("Create Letter" feature)

UI:

client/src/pages/letters.tsx

Shows violations by bureau

Lets user select violations and trigger generation

Uses /api/dispute-letters data to show history and print previews

Backend endpoint:
POST /api/dispute-letters/generate (in server/routes.ts)

Backend logic:

Validates request via Zod:

bureau (EQUIFAX, TRANSUNION, EXPERIAN)

violationIds[] (must be non-empty)

round (1–3)

recipientType (BUREAU vs COLLECTOR)

Optional: recipientName, priorDisputeDate, craResponseDate, reportDate

Loads:

Current user (from users table)

All violations for that user, then filters by violationIds

Builds userInfo (name/address/phone/email/dob) from DB

If recipientType === 'BUREAU':

Currently uses generateRoundBasedLetter(...) from:

server/services/roundLetterTemplates.ts

That template:

Structures letter around Round 1 / 2 / 3 logic

Explicitly calls out duties under FCRA and Metro2

Injects each selected violation as:

Creditor name

Account number

Issue description

Requested action

If recipientType === 'COLLECTOR':

Uses generateCollectorValidationLetter(...) from:

server/services/collectorLetterTemplates.ts

Template focuses on FDCPA validation language and consumer rights.

Persists generated letter into disputeLetters table with:

userId, bureau, letterType, round

recipientType, recipientName

content (full letter body)

pdfUrl and status (GENERATED / SENT, etc.)

If plan = DONE_FOR_YOU:

Uses click2mailService to send letter automatically.

Updates status via storage.updateDisputeLetterStatus(...).

Key point for your requirement:

The violations that drive letter content are produced by the GPT-5.1-based analysis + rules engine, with explicit FCRA / Metro2 / FDCPA tagging.

The letters themselves are generated via deterministic templates that use those AI-derived violations & statutes to populate the letter content.

So, from the user’s POV on production:

Upload → GPT-5.1 parses & analyzes report with FCRA/Metro2/FDCPA logic.

Violations appear under Letters tab.
